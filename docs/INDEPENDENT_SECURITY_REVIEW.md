Reviewer: a separate AI review agent, explicitly authorized by the owner, examining the implementation independently of the builder's earlier security conclusions. ## Verdict

The baseline contains substantive security controls and the availability findings below. Their working-source corrections have been reviewed and component-tested as described in the addendum. **Public exposure still requires fresh full-stack verification and deployment acceptance checks.** Three independently reproduced boundary gaps and two source-confirmed persistent-capacity gaps were found. No authentication bypass, cross-workspace data disclosure, arbitrary arithmetic execution, or automatic paid-provider fallback was identified in the reviewed paths. That statement describes the review's observations; it is not proof that such flaws cannot exist.

The builder was notified before this report was written and implemented corrections. The addendum below records independently inspected fixes and executed component checks. Fresh full integration/scanner results remain separate release requirements; they are not inferred from this review.

## Findings

### ISR-01 â€” High: unauthenticated slow bodies can exhaust all mutation slots

Baseline locations: `frontend/src/app/api/[...path]/route.ts:58â€“71,126`; `backend/quarry/api.py:121`; `infra/Caddyfile:1â€“15`; `infra/Production.Caddyfile:1â€“15`.

The BFF increments a process-wide eight-request mutation counter before reading a request body. Each `reader.read()` can wait indefinitely; there is neither a body-read deadline nor cancellation on a server timer. Slot release occurs only when the handler exits. Caddy limits bytes but does not configure header/body read deadlines. The API independently buffers incoming bodies without an absolute read deadline. Byte limits and concurrency limits therefore do not bound the lifetime of admission resources.

A client can send the application's public Origin header, open eight mutation requests without valid credentials, and keep their bodies unfinished. Authentication happens downstream after body collection. Subsequent legitimate mutations receive 503 on that replica. More replicas increase the number of connections required; they do not remove the failure mode. The isolated original-module probe reproduced slot exhaustion and recovery after release. The probe did not attack the running application or quantify an internet-scale outage.

Remediation: add bounded header and body deadlines at Caddy, an absolute BFF body-read deadline that cancels the reader, and an API body-read deadline. Propagate aborts to non-streaming upstream requests, release slots in `finally`, retain durable SSE reconnect behavior, and test that slow bodies time out and capacity becomes available again.

### ISR-02 â€” Medium: continuously active public responses bypass the run wall budget

Baseline locations: `backend/quarry/network.py:18,51,55,93`; `backend/quarry/agent.py:105â€“110,188â€“193`; `backend/quarry/queue.py:165â€“171,180â€“192`.

The public fetcher uses an eight-second socket inactivity timeout and one blocking `response.read(max_bytes + 1)`. Neither socket inactivity nor maximum bytes establishes an absolute operation deadline. An attacker controlling a permitted public URL can deliver bytes more frequently than the inactivity timeout and retain the worker for substantially longer than the advertised 180-second run budget. The worker checks that budget before and after stage actions, while its heartbeat continues renewing the lease during a blocked fetch. DNS lookup is also outside a bounded total fetch operation.

The isolated loopback probe demonstrates the timeout behavior with proportionally short intervals. It does not demonstrate private-network reachability: the address-pinning/public-IP checks were separately inspected and no bypass was found.

Remediation: bound the entire fetch, including DNS, connection, headers, redirects, and streaming body, by one monotonic deadline. Read bounded chunks and recompute the remaining budget; do not rely solely on setting a socket timeout before a blocking full-body read. Cancellation/run-budget checks must stop actual work, not merely reject its eventual result. Test a response that continually supplies data, delayed DNS, and multiple redirects against one shared deadline.

### ISR-03 â€” Medium: public PDF fetching bypasses resource-bounded parsing

Baseline locations: `backend/quarry/tools.py:69â€“74`; compare `backend/quarry/worker.py:27` and `backend/quarry/ingest.py:15â€“40`.

Uploaded files are parsed in a subprocess with memory/CPU/file-descriptor limits and a 25-second parent timeout. The `fetch_url` tool passes attacker-controlled public content directly to `extract` in the main worker. Since the fetcher's accepted types include PDF, this provides a different path into the same PDF parser without those limits. A compressed/complex PDF below the download byte cap can consume worker CPU or expanded memory; the parent worker contains application credentials and serves other queued tenants. The container's memory ceiling is an eventual process-kill boundary, not equivalent to a bounded disposable parser.

The parser-spy probe confirmed in-process PDF dispatch. No resource bomb or parser RCE was executed, so this report does not claim to have demonstrated a specific PDF exploit or remote code execution.

Remediation: route fetched content through the same resource-bounded parsing entry point as uploaded content. Test the fetched-PDF path explicitly, including parser timeout/termination and the continued availability of the worker.

### ISR-04 â€” Medium: conversation metadata grows outside workspace storage/job limits

Baseline location: `backend/quarry/api.py:521â€“527`; `backend/quarry/capacity.py` accounts for source object bytes and jobs, not conversation rows.

Every authenticated writer POST to `/v1/conversations` inserts a persistent row. This path has no request limiter, record-count ceiling, shared admission control, or cleanup of abandoned empty conversations. A single verified public-signup account can repeatedly create empty conversations while remaining below document-byte and job quotas. Listing only 100 rows does not bound stored rows. This is a source-confirmed persistent resource-consumption path, not a reproduced database-filling incident; the reviewer deliberately did not flood the primary database.

Remediation: establish an explicit per-workspace conversation limit, serialize its check with creation, apply the shared per-workspace request limiter, and make the limit visible/actionable. A retention/deletion policy for empty/old conversations may complement the hard bound. Test concurrent requests around the ceiling in the isolated test database.

### ISR-05 â€” Medium: tiny sources amplify retained database/vector metadata outside byte quotas

Baseline location: `backend/quarry/api.py:306â€“397` (`add_document`); `backend/quarry/worker.py:17â€“79`; `backend/quarry/retrieval.py:68â€“93`.

Source storage admission sums original document bytes, but imposes no retained-document count ceiling. A stream of unique short documents consumes little of the source-byte allowance while creating a document row, chunk rows and vector-index records for every source. The upload rate and queue limits constrain arrival rate and concurrency, but completed sources remain indefinitely, and the source-byte counter does not represent their expanded database/index footprint. Superseding/deleting a source also retains its document metadata row. A persistent owner can therefore cause significantly more retained database/vector storage than the advertised object-byte quota suggests. This is a source-confirmed amplification path; no database-filling load was run.

Remediation: impose an explicit retained-document count ceiling under the existing serialized admission/workspace transaction. Count tombstones and superseded records until an operator retention process actually removes their metadata. Document the difference between source-byte quotas and full storage capacity, expose the count/limit, and test simultaneous near-limit admissions. Quota reconciliation of orphaned objects and real physical disk monitoring remain useful operational controls.

## Controls that survived this review's inspection

- Passwords use bounded Argon2id verification; unknown-account login follows a dummy hash path; authenticated sessions are random opaque tokens stored as keyed digests. Session lookup checks disabled accounts and expiration, and production rejects pre-existing demo identities.
- Login and sensitive account actions use shared PostgreSQL throttles. Token redemption, password/MFA changes and recovery-code consumption use row locks; recovery/reset paths revoke sessions and machine keys as appropriate. Password reset preserves enabled MFA.
- Owner/editor/viewer requirements are evaluated server-side. Inspected documents, research, exports, conversation, member and invitation paths apply workspace ownership filters; dense/sparse retrieval combines workspace and published-document filters with a post-query activity check.
- BFF cookie mutations require the configured Origin; bearer-key mode strips cookies and the backend validates/restricts machine credentials. External gateway client-IP headers are replaced, and the backend only accepts signed private proxy metadata. Changing this ingress topology requires reviewing that trust boundary again.
- Public fetch URLs reject credentials, unusual ports and non-public resolved addresses, revalidate redirects, connect to a pinned address, and retain the original TLS hostname. Arithmetic uses a bounded AST allowlist, not dynamic evaluation.
- Source passages render as text; source links require HTTP(S) and use `noopener noreferrer`. Source instructions are not granted new server permissions. Prompt-level instructions alone are not a general prompt-injection guarantee.
- Paid-provider calls require both deployment configuration and explicit per-run consent. Free exhaustion preserves the chosen provider; no inspected branch automatically selected a paid provider. The software cannot verify whether an operator's Groq organization is actually on a free billing plan.
- Job result and checkpoint publication use lease/fence checks under row locks, and cancellation is checked at publication. Private S3 control-plane listeners and a narrow S3 gateway reduce exposure. Runtime SQL credentials are separated from migration credentials.

These are code-inspection conclusions, not an independent rerun of every existing integration test.

## Residual concerns and deployment conditions

1. The **baseline** parser child shares its worker UID/filesystem/network namespace. The builder has since introduced a separate credentialless parser container under UID 10002, no network, a read-only root, dropped capabilities, PID/memory limits and a private Unix socket. Read-only inspection of the actual running parser container confirmed these isolation settings, as detailed in the addendum. This materially narrows credential/process exposure. It is still not a per-document hostile-code sandbox: hypothetical arbitrary parser code execution could compromise the shared parser service or its writable socket and affect later parsing requests. No parser RCE, credential escape, or cross-request attack was demonstrated. Runtime configuration and isolation must be checked on the actual deployment host.
2. Public production hosting, TLS issuance, mail deliverability/TLS, DNS, backups outside the host, and restore operations on the chosen host require live acceptance checks. A local Compose report cannot substantiate those checks.
3. Public signup introduces abuse and email-delivery costs/caps even when model use is free. Source/job/model quotas do not substitute for ingress protections, metadata limits, account-abuse operations, and infrastructure monitoring.
4. The optional evaluation environment's known package advisories and local capability-removal patches remain a separate disclosed exception. Scanner success must retain those raw findings and mitigation evidence. They must not be presented as upstream fixes or a vulnerability-free dependency set.
5. Free hosting can reclaim or suspend capacity. Multi-host database/storage failure recovery, hostile multi-tenant stress, and service-level objectives were not established by this review.

Additional retained-metadata hardening was independently inspected after the initial five corrections:

- Research admission now caps retained runs at 10,000 per workspace under the existing admission/workspace lock. Exact idempotent replay is checked before the new ceiling, so replay at capacity does not create another row or consume a fresh slot.
- Invitation redemption holds the workspace row lock while counting all members (including disabled accounts) and inserting a new member, with a default ceiling of 100. It does not acquire the invitation advisory lock.
- Invitation issuance serializes pending-invitation count/replacement under a transaction-scoped PostgreSQL advisory lock derived from a signed 64-bit SHA-256 prefix of the workspace namespace. Reissuing to an already pending address does not consume another pending slot. The first implementation used an overlong scheduler-table key; independent review identified that schema-length error, and the final source uses the advisory lock instead. No schema-length bypass is required.
- The invitation path takes its advisory lock before token replacement and queue admission, while redemption takes the token then workspace row. Research admission takes admission then workspace. No inspected path acquires the invitation advisory lock after holding the workspace/token resources, so this change introduces no identified reverse-lock cycle. A collision in the 64-bit advisory namespace would serialize unrelated issuances rather than grant access.
- Retained run/member counts and configured limits are exposed by the scoped usage endpoint. These are source-inspection conclusions; this reviewer did not run concurrent PostgreSQL tests or the enlarged release suite.
